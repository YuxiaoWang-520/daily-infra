1482: #### Constraints
1483: 
1484: A set of ops is *capturable* if it doesn't violate any of the following constraints.
1485: 
1486: Constraints apply to all work in a
1487: {class}`torch.cuda.graph` context and all work in the forward and backward passes
1488: of any callable you pass to {func}`torch.cuda.make_graphed_callables`.
1489: 
1490: Violating any of these will likely cause a runtime error:
1491: 
1492: * Capture must occur on a non-default stream. (This is only a concern if you use the raw
1493:   {meth}`CUDAGraph.capture_begin<torch.cuda.CUDAGraph.capture_begin>` and
1494:   {meth}`CUDAGraph.capture_end<torch.cuda.CUDAGraph.capture_end>` calls.
1495:   {class}`~torch.cuda.graph` and
1496:   {func}`~torch.cuda.make_graphed_callables` set a side stream for you.)
1497: * Ops that synchronize the CPU with the GPU (e.g., `.item()` calls) are prohibited.
1498: * CUDA RNG operations are permitted, and when using multiple {class}`torch.Generator` instances within a graph,
1499:   Avoid using {meth}`Generator.get_state<torch.get_state>` and {meth}`Generator.set_state<torch.set_state>` during capture;
1500:   instead, utilize {meth}`Generator.graphsafe_set_state<torch.Generator.graphsafe_set_state>` and {meth}`Generator.graphsafe_get_state<torch.Generator.graphsafe_get_state>`
1501:   for managing generator states safely within the graph context. This ensures proper RNG operation and generator management within CUDA graphs.
1502: * Dynamic control flow (based on CPU or GPU data) is prohibited, unless it is based on GPU data and implemented via higher order operator
1503:   torch.cond(). See {ref}`Data Dependent Control Flow<graph-data-dependent-control-flow>`.
1504: 
1505: 
1506: Violating any of these will likely cause silent numerical errors or undefined behavior:
1507: 
1508: * Within a process, only one capture may be underway at a time.
1509: * No non-captured CUDA work may run in this process (on any thread) while capture is underway.
1510: * CPU work is not captured. If the captured ops include CPU work, that work will be elided during replay.
1511: * Every replay reads from and writes to the same (virtual) memory addresses.
1512: * Dynamic shapes are prohibited. The graph assumes every tensor in the captured op sequence
1513:   has the same size and layout in every replay.
1514: * Using multiple streams in a capture is allowed, but there are {ref}`restrictions<multistream-capture>`.

1766: ### Graph memory management
1767: 
1768: A captured graph acts on the same virtual addresses every time it replays.
1769: If PyTorch frees the memory, a later replay can hit an illegal memory access.
1770: If PyTorch reassigns the memory to new tensors, the replay can corrupt the values
1771: seen by those tensors.  Therefore, the virtual addresses used by the graph must be
1772: reserved for the graph across replays. The PyTorch caching allocator achieves this
1773: by detecting when capture is underway and satisfying the capture's allocations
1774: from a graph-private memory pool. The private pool stays alive until its
1775: {class}`~torch.cuda.CUDAGraph` object and all tensors created during capture
1776: go out of scope.
1777: 
1778: Private pools are maintained automatically. By default, the allocator creates a
1779: separate private pool for each capture. If you capture multiple graphs,
1780: this conservative approach ensures graph replays never corrupt each other's values,
1781: but sometimes needlessly wastes memory.
1782: 
1783: #### Sharing memory across captures
1784: 
1785: To economize the memory stashed in private pools, {class}`torch.cuda.graph`
1786: and {func}`torch.cuda.make_graphed_callables` optionally allow different
1787: captures to share the same private pool.
1788: It's safe for a set of graphs to share a private pool if you know they'll always
1789: be replayed in the same order they were captured,
1790: and never be replayed concurrently.
1791:

1859: ### Data Dependent Control Flow
1860: 
1861: Data-dependent control flow can with cuda graphs if the control flow
1862: is implemented using torch.cond(). If your function uses this
1863: function, compiling it with the "cudagraphs" backend will enable
1864: control flow in the resulting cuda graph via [conditional nodes](https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes/).
1865: 
1866: Doing cuda graph capture of eager mode code using torch.cond() will
1867: also work.
1868: 
1869: Support for inductor backend to torch.compile is not available yet,
1870: but there is no fundamental blocker.
1871: 
1872: An example of using the cudagraphs backend to torch.compile on code
1873: using torch.cond is demonstrated below:
1874: 
1875: ```python
1876: import torch
1877: 
1878: def true_fn(x):
1879:     return x.sin()
1880: 
1881: def false_fn(x):
1882:     return x.cos()
1883: 
1884: x = torch.randn(4, device="cuda", requires_grad=False)
1885: pred = torch.tensor(False, device="cuda", requires_grad=False)
1886: def foo(pred, x):
1887:     with torch.inference_mode():
1888:         return torch.cond(pred, true_fn, false_fn, [x])
