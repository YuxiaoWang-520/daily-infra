# 写作与审查规范

## 发布标准

每篇 Wiki 应让没有该主题经验的读者，沿着“问题 → 直觉 → 最小例子 → 原理 → 实现 → 工程取舍 → 动手验证”完成学习，并能回答逐层深入的面试追问。一天聚焦一个核心问题，深度来自推导与证据，篇幅服从讲清问题的需要。

主问题须对应常见工程场景。正文开头先给出简明结论、使用场景和学习目标，再展开推导。不要用行业名词列表或论文摘要代替解释。

## 文章结构

使用 [正文模板](../templates/article.md)，根据问题调整小节，但保留以下内容。

1. **主问题与真实场景**：说明输入、约束、想优化的指标以及为何值得研究。
2. **必要基础**：首次出现的术语就地解释；前置知识未发布时给出最小补充。
3. **具体例子与图解**：用小尺寸输入或具体数字走一遍数据流、内存布局或执行时序。图中的对象、箭头、单位与正文一致。
4. **推导与实现**：解释公式中的符号、假设与单位，再追踪实际代码中的入口、关键状态和执行路径。
5. **优化与取舍**：说明优化改变了哪项成本，何时适用、何时收益消失、会付出哪些代价，以及怎样验证。
6. **代码练习**：至少两道，基础题用于建立模型，进阶题用于分析工程情境。题目写清输入、输出、约束和验收条件。
7. **详解答案**：可在正文使用 `<details>` 折叠，完整代码同时归档。给出解题过程、运行命令、预期结果、边界条件与常见错误。
8. **面试追问**：至少覆盖基础解释、实现分析、方案选择和排障验证四个层次，附参考回答要点。
9. **适用范围与延伸**：列出教学简化、未验证部分、前置文章和后续问题。

图解优先选择 Mermaid 的流程图、时序图或状态图。复杂内存图或数据图可用 SVG 和标准绘图工具，保留图源；不能把未经核验的示意图当作实际 trace。

## 研究与证据

### 来源选择

- 外部技术结论优先使用官方仓库、官方文档、原始论文及作者发布的实现。
- 二手文章可以帮助定位资料，但不能单独支撑核心实现、性能或算法正确性结论。
- 先列出本篇需要证实的关键论断，再查证据，避免先写结论后找相似引文。
- 使用 [资料模板](../templates/references.md)，把核心论断和资料定位逐项对应。

### 源码核验

- 涉及引擎设计，必须实际 clone 或 fetch 最新官方源码。仅浏览 README、引用旧博客或只列仓库首页不能代替代码分析。
- “最新”仅指本次检索时已经核验的分支和 commit。记录官方远端、默认分支、完整 SHA、获取时间、版本／tag（若有）以及选择该版本的理由。
- 区分默认分支与稳定发布版本，不能把默认分支的行为说成已经发布或线上默认采用。
- 从实际入口追踪关键函数、状态和数据结构；对受 feature flag、backend、硬件或模型配置影响的分支说明生效条件。
- 正文提供固定 commit 的源码永久链接，并引用函数或符号；本地证据保留相关路径、必要片段、许可证信息和读取说明。不要把浮动的 `main` 链接当作版本证据。
- 上游缓存若已存在，先检查是否有修改；不得重置或清理他人改动。新建缓存按需使用 shallow／sparse checkout，避免下载无关权重与数据集。

### 论文与算法核验

- 介绍具体算法时阅读原始论文的相关章节、公式或伪代码，并对照作者或可信官方实现。
- 记录论文题名、作者、发布日期、版本、DOI／arXiv ID／官方 URL 和访问日期；引用准确章节、公式、图或算法编号。
- 归档自己的阅读笔记，解释符号、前提、关键推导和实现对应关系。原文按可再分发条件归档，未归档时说明原因并保留可定位来源。
- 论文假设与工程实现不一致时，明确指出差异及影响；教学伪代码也要说明省略内容。
- 对纯基础语义主题可使用官方规范与实现，无需强行寻找不相关论文；记录不涉及具体论文算法的原因。

## 练习与实验

- 基础练习尽量可在普通 CPU 环境运行；GPU 扩展练习给出硬件要求、依赖版本、正确性条件和完整命令。
- 题目与答案分开，不能要求读者先看到答案才能理解题目。参考实现须完整，不能只给关键几行。
- 运行参考答案，并以能够发现实际错误的断言、测试或对照结果验证关键行为。覆盖本题重要的边界条件。
- 记录实际命令、退出码、环境与输出。没有执行的代码明确标为未执行，不能伪造输出；核心基础练习未验证时不满足发布标准。
- 不为完成文章自动安装或升级全局依赖；优先使用现有环境与标准库。必要环境缺失时选择仍能验证核心问题的实现，或保留草稿。
- 对 GPU 性能测量说明输入 shape、dtype、layout、设备、软件版本、warmup、同步、重复次数和统计口径。给出精度标准与基线；吞吐、端到端延迟、TTFT、ITL、显存容量等指标不能混用。
- 理论估算、CPU 教学实验、GPU 微基准与生产服务结果分别标注；不能从其中一种直接推出其他结论。

## 两轮审查

使用 [审查模板](../templates/review.md) 保存每轮审查发现与修正。两轮可以由同一执行者自审，但必须如实标明；如果使用独立审查者，记录其真实角色和范围。

第一轮检查技术事实：核心论断是否有直接证据，源码是否确实拉取并固定版本，公式和例子能否复算，论文与代码是否对应，练习是否通过，性能结论是否越过证据边界。

第二轮检查教学表达：主问题能否贯穿全文，是否从必要基础逐步深入，术语与图解是否清楚，代码是否解释关键步骤，习题答案能否帮助排查错误，工程场景和取舍是否具体。

审查中发现的问题分为 CRITICAL（阻断）、HIGH（警告）、MEDIUM（信息）、LOW（提示）。存在 CRITICAL 或 HIGH 时不得发布；影响核心理解的 MEDIUM 也应先修复。审查记录必须有实际观察、修改和复验结果，不能仅机械勾选清单。

## 归档与幂等发布

1. 使用上海日期 `YYYY-MM-DD`，选择未发布且前置知识足够的一个问题。
2. 在 `drafts/YYYY-MM-DD-topic/` 中研究、写作、运行练习并审查；每次都保留可恢复的工作状态。
3. 通过审查后将完整目录放到 `wiki/YYYY/MM/YYYY-MM-DD-topic/`，检查相对链接、图源、资料、代码与审查记录是否齐全，再更新 `wiki/index.md`。
4. 确认索引与文章发布状态一致；中断后重复运行应恢复同一篇，不能为同一天创建第二篇。
5. 当天已经发布时只核验完成状态，必要时修正错误并追加勘误，不新增重复文章。
6. 若存在阻塞，保存草稿和具体缺口并报告失败。可以缩小选题到仍然完整的核心问题，但不能为满足频率而降低证据标准。
7. 未自动运行的日期不在后续一天批量补发；下一次运行继续学习顺序，每个实际发布日最多一篇。

发布是本地归档和索引更新；Git 提交、推送和外部站点发布不包含在本流程中。
