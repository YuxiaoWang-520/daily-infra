# 每日 Wiki 任务

在 `/Users/wangyuxiao/Documents/ChatGPT/daily-infra` 中，按照 `AGENTS.md`、`docs/EDITORIAL.md`、`ROADMAP.md` 和 `templates/` 的规范，完成并归档当天的一篇 AI Infra 中文知识 Wiki。目标读者从零开始学习，以面试官的问题链逐步成长为能解释原理、读懂代码、验证优化、处理真实问题的全栈工程师。

## 每次运行

1. 以 `Asia/Shanghai` 计算日期；仅周一至周五执行，不考虑节假日调休。检查仓库状态、`wiki/index.md`、已有文章与草稿；保护无关改动。先恢复已审查文章未完成的 Git 同步；当天已经发布则不重复产出。
2. 从前置知识最充分的下一题开始，选择一个有常见工程用途的核心问题。首次从 Tensor 的 shape、stride 与连续性开始。选题不限于现有路线，持续覆盖算子、编译与执行、训练并行、推理引擎、算法、内存、Cache、存储、网络、资源管理与可靠性。
3. 实际调研当日一手资料。涉及引擎必须 clone 或 fetch 对应官方最新源码，固定完整 commit，并读取实际调用路径。算法主题必须阅读原始论文并与实现核对。记录检索时间、版本、来源定位和适用条件；不得凭记忆声称最新，不得将主分支行为说成稳定发布行为。
4. 用正文模板写作：真实场景和结论开篇，从直觉、基础术语、具体数字示例到公式、图解和源码逐层深入，说明优化适用条件、代价、验证方法和常见误区。至少一幅有解释价值的图，并给出由浅入深的面试追问及参考回答。
5. 提供至少两道代码练习及完整详解答案、运行方法、验收条件与边界情况；运行基础答案并保存真实验证记录。尽量提供 CPU 可运行的入门练习，GPU 专属部分如实记录验证范围。不可自动安装或升级全局依赖，不能把未运行结果写成通过。
6. 用资料模板归档引用、阅读笔记、关键源码证据与论文笔记，给出固定 commit 的链接和准确章节／符号定位。原始资料按可获取与可再分发条件保存；未保存原文时说明原因。源码缓存放 `.cache/upstream/`，发布证据须留在当篇目录，不能只留外部链接。
7. 执行技术证据与教学表达两轮审查，修复问题，保存实际审查和复验记录，标明自审或独立审查。遵守代码语言对应的审查要求。核心证据缺失、基础答案未验证或有 CRITICAL／HIGH 问题时保存草稿并报告阻塞，不得宣称发布。
8. 审查通过后，将完整内容归档到 `wiki/YYYY/MM/YYYY-MM-DD-topic/`，更新 `wiki/index.md`，检查本篇链接、图源、题目、答案、资料和审查记录。每个上海日期最多一篇新文章；重复运行恢复同一篇，错过日期不集中补发。
9. 按下述 Git 同步流程，自动提交并推送已审查内容到私密仓库。GitHub 远端确认包含该提交后，才能报告本篇已完成同步。

## Git 同步流程

用户已授权本任务自动提交并推送通过审查的新文章及必要勘误，无需逐次确认。目标固定为私密仓库 [YuxiaoWang-520/daily-infra](https://github.com/YuxiaoWang-520/daily-infra)，本地 `main` 分支与远端 `origin/main`。

1. 开始前记录分支、远端、工作区、暂存区和未推送提交。核验当前分支为 `main`、`origin` 的读取与推送地址均指向上述仓库（允许 GitHub SSH 或 HTTPS 地址），并确认仓库仍为私密。使用仓库级 GitHub 身份 `YuxiaoWang-520 <13917046839@163.com>`；不得使用公司身份提交。
2. 拉取远端状态。需要更新本地分支时，仅在不会覆盖无关改动的条件下快进同步；不自动 stash、rebase、reset 或清理用户文件。分支、远端、可见性异常，存在冲突，或待推送范围含无关提交时，保留工作并报告同步阻塞，不替用户处理无关改动。
3. 两轮审查、必要测试和交付检查通过后，按具体路径暂存本篇目录、`wiki/index.md`，以及本篇确实需要且已审查的 `README.md`／`ROADMAP.md` 更新。不得使用 `git add .` 或 `git add -A`。不提交 `playground/`、缓存、IDE 配置、未通过审查的草稿或任何无关改动；暂存区已有无关内容时不创建混合提交，也不擅自撤销用户暂存。
4. 检查暂存差异与文件清单，运行 `git diff --cached --check`，确认没有凭据或无关文件。使用 conventional commit，例如 `docs: add YYYY-MM-DD <topic>`；勘误也须通过对应审查和验证。没有变化时不创建空提交。
5. 正常推送至 `origin/main`，不强制推送。推送后核验 GitHub 的 `main` 分支包含该提交，记录提交 SHA 和提交链接；不修改仓库可见性、不创建 PR、不部署，也不向他人发送消息。
6. 提交或推送失败时保留文章、审查记录和已经创建的提交，报告失败步骤及原因，区分“已本地归档”“已提交未推送”和“已同步到 GitHub”。下次运行优先恢复尚未完成的同步；已提交则复用原提交，已同步则不重复提交或新增同日文章。远端出现分歧时保留现状并报告，不强行改写历史。

## 完成报告

成功时给出文章标题、核心问题、正文与练习的可点击本地链接、资料版本、验证摘要、GitHub 提交链接和下一篇候选题。失败时给出草稿或文章位置、失败步骤、缺少的具体证据、Git 同步状态以及可继续工作的状态。不得把仅创建目录、只有提纲、未审查的正文或尚未推送的提交报告为全部完成。

只有新文章完成、重要勘误、任务失败或需要用户处理时才报告；当天已经完成且没有重要变化时保持安静。
