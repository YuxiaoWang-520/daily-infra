# 脱敏与知识重建

目标是让文档脱离来源项目仍然成立。即使目的仓库是私密仓库，也按可公开技术知识的标准整理；仓库私密属性不是复制内部资料的许可。

## 保留什么，怎样改写

| 材料 | 处理方式 |
| --- | --- |
| 通用机制、公开 API、公式与已公开算法 | 保留准确语义和必要参数，用公开的一手证据核验。 |
| 公司、客户、人员、产品代号、内部模型或硬件代号 | 删除身份信息，改为“推理服务”“缓存模块”等必要的通用角色。公开库名如 PyTorch 可保留。 |
| 内部仓库、分支、commit、工单、任务、实例或请求 ID | 不进正文、图源、引用、提交信息和证据；用公开实现重新解释，不能仅去掉域名。 |
| 地址、内部域名、端点、账号、用户目录、对象存储路径 | 删除或换成不具可访问性的教学占位符；同时检查异常栈、命令和图像元数据。 |
| Token、密钥、Cookie、认证头、连接串及真实用户数据 | 不复制、不输出、不保存替换映射或带原值的审查记录。 |
| 私有代码、生产配置、日志、截图、trace、数据集或权重 | 留在原项目；用自主编写的最小示例、合成输入和公开资料重建机制。改名不能消除其保密性。 |
| 业务规模、生产故障、未公开性能、成本和资源配比 | 去掉项目事实。必要时构造新的教学数字并说明是假设或合成实验；不保留可识别的组合特征。 |

技术常量不为脱敏而改错，例如 BF16 的位分配、公开算法的公式、API 参数及必须满足的整除约束。改写输入尺寸或时序后，重新计算所有结果并验证机制仍成立。

## 写入前的处理顺序

1. 在当前任务上下文中列出要解释的通用问题与所需条件；不把原始材料搬到目标仓库“以后再删”。临时核验留在来源项目或仓库外，不自动遍历其他项目。
2. 判断机制本身是否可以公开解释。若只有私有实现或受限制的算法才成立，不以换名方式包装；转为有公开证据的更一般问题，或保留未完成状态。
3. 用最小的合成数据和自编教学代码重建例子。重新验证结果，标清教学简化；公开源码片段注明版本与许可。
4. 归档公开来源笔记和合成运行输出。审查记录只写“去掉了业务身份信息”“改用合成时序”等类别，不记原值及原值到假名的映射。
5. 从完整交付和待推送差异反向检查：陌生读者能否由标识、规模、精确时间和数字组合识别原项目？是否夹带与解释机制无关的私有信息？有疑问就缩小内容。

## 同时检查正文之外的文件

检查文件名、目录名、Markdown 链接、图片及图源、代码注释、命令参数、环境记录、JSON／CSV 输出、引用、审查记录和提交信息。需要环境信息时保存解释结果所需的公开软件版本与设备能力，不保存主机名、租户或完整环境变量。

可以对本次文件做凭据或标识扫描，但扫描不能替代人工语义审查。命中时只报告文件位置和风险类别，不在工具输出中打印可能敏感的整行。任何实际敏感文件都不暂存；暂存差异也不能先推送再补删。

仅凭“字串搜索无命中”不能证明私有算法已变成公开知识。公开出处和独立重建的例子是必须一起检查的证据。

## 一个虚构示例

虚构素材描述“某服务、某租户的一次运行中，计时结果异常”，并附有内部链接、请求 ID 与设备日志。可提炼的问题是：**异步设备执行时，为什么主机计时可能测不到完整执行时间？**

成文时不重述该事件：用公开 API 和合成任务解释提交与执行的区别，画出通用时序图，说明计时边界与同步条件；根据实际环境记录 CPU 示意或 GPU 实测。先检索已有计时文章，若原理已经覆盖，只补充确实缺少的边界或反例。

不把原服务、租户、事件日期、日志摘录或原始延迟带入文档；合成时序也不能标成来自生产的实测 trace。
